Élevée M365-APP-002 - Applications tierces avec permissions à haut privilège non vérifiées ou consenties par un utilisateur (2 élément(s), Sous 30 jours)
Preuves

Pourquoi c'est important : Une application avec Mail.ReadWrite ou Directory.ReadWrite.All est un compte de service invisible : elle lit ou modifie les données sans connexion interactive, sans MFA, souvent sans que personne ne se souvienne de l'avoir autorisée.

Élevée M365-CA-002 - MFA non imposée à tous les utilisateurs (2 élément(s), Sous 30 jours)
Preuves
  • aucune stratégie active 'Tous les utilisateurs + toutes les applications + MFA'
  • stratégies MFA partielles (périmètre réduit) : CA01 - MFA pour les rôles d'administration

Pourquoi c'est important : Microsoft estime que la MFA bloque l'immense majorité des attaques automatisées sur les comptes. Sans MFA imposée à tous, un mot de passe hameçonné ou réutilisé ailleurs donne directement accès à la boîte mail et aux fichiers.

Remédiation : Créer une stratégie d'accès conditionnel 'Tous les utilisateurs / Toutes les ressources / Exiger l'authentification multifacteur' en excluant uniquement les comptes de secours (break-glass). Viser ensuite une MFA résistante à l'hameçonnage (FIDO2, Windows Hello, passkeys).

Licence : Accès conditionnel : Entra ID P1 (sinon : security defaults).

Références : CIS M365 Foundations — 'Ensure multifactor authentication is enabled for all users' ; SCuBA MS.AAD.3.2v2 — MFA SHALL be enforced for all users ; SCuBA MS.AAD.3.1v1 — Phishing-resistant MFA SHALL be enforced for all users
MITRE ATT&CK : T1078.004 Valid Accounts: Cloud Accounts, T1110.003 Brute Force: Password Spraying

Élevée M365-COL-002 - Domaine personnalisé sans DKIM, DMARC appliqué ou SPF strict (6 élément(s), Sous 30 jours)
Preuves
  • agrisouss-export.com : aucun enregistrement SPF
  • agrisouss-export.com : signature DKIM désactivée
  • agrisouss-export.com : aucun enregistrement DMARC
  • agrisouss.ma : SPF non strict (v=spf1 include:spf.protection.outlook.com ?all)
  • agrisouss.ma : signature DKIM désactivée
  • agrisouss.ma : DMARC p=none (surveillance seulement)

Pourquoi c'est important : Sans SPF, DKIM et DMARC en mode quarantine/reject, n'importe qui peut envoyer un e-mail qui semble venir de @agrisouss.ma : faux ordre de virement au comptable, fausse facture au client. DMARC 'p=none' observe mais ne protège pas.

Remédiation : Publier un SPF qui se termine par -all (ou ~all transitoire), activer la signature DKIM dans Defender (2 CNAME selector1/selector2), publier DMARC p=none avec rapports, analyser 2-4 semaines, puis passer en quarantine puis reject.

Références : CIS M365 Foundations — 'Ensure DKIM is enabled for all Exchange Online Domains' ; CIS M365 Foundations — 'Ensure DMARC Records for all Exchange Online domains are published' ; CIS M365 Foundations — 'Ensure SPF records are published for all Exchange Domains' ; SCuBA MS.EXO.2.2v3 (SPF), MS.EXO.3.1v1 (DKIM), MS.EXO.4.1v1 / MS.EXO.4.2v1 (DMARC p=reject)
MITRE ATT&CK : T1566 Phishing, T1684.002 Social Engineering: Email Spoofing

Élevée M365-PRIV-001 - Nombre d'administrateurs généraux (Global Administrator) hors de la plage recommandée (1 élément(s), Sous 30 jours)

Pourquoi c'est important : Global Administrator peut tout faire dans le tenant. Trop de titulaires multiplie les comptes dont la compromission est fatale ; un seul titulaire crée un risque de blocage total s'il est perdu (départ, MFA perdue).

Preuves
  • y.benali@agrisouss.ma : 'Exchange Administrator' actif sans date de fin
  • f.bakkali@agrisouss.ma : 'Global Administrator' actif sans date de fin
  • h.alaoui@agrisouss.ma : 'Global Administrator' actif sans date de fin
  • k.idrissi@agrisouss.ma : 'Global Administrator' actif sans date de fin
  • s.mansouri@agrisouss.ma : 'Global Administrator' actif sans date de fin
  • y.benali@agrisouss.ma : 'Global Administrator' actif sans date de fin

Pourquoi c'est important : Une attribution 'active permanente' signifie que le compte est administrateur 24 h/24, même quand personne n'administre. Avec Privileged Identity Management (PIM), le rôle est 'éligible' et activé pour quelques heures, avec justification et MFA : la fenêtre d'exposition chute fortement.

Remédiation : Convertir les attributions actives permanentes en attributions éligibles PIM (activation limitée dans le temps, MFA, approbation pour Global Administrator). Seuls les comptes de secours restent actifs en permanence.

Licence : PIM nécessite Entra ID P2 (ou Entra ID Governance).

Références : CIS M365 Foundations — 'Ensure Privileged Identity Management is used to manage roles' ; SCuBA MS.AAD.7.4v1 — Permanent active role assignments SHALL NOT be allowed for highly privileged roles ; SCuBA MS.AAD.7.6v1 — Activation of the Global Administrator role SHALL require approval

Élevée M365-PRIV-004 - Comptes d'accès d'urgence (break-glass) absents, incomplets ou non surveillés (2 élément(s), Sous 30 jours)
Preuves

  • aucune alerte configurée sur les connexions des comptes break-glass

Pourquoi c'est important : Si la MFA tombe en panne ou si un administrateur se bloque avec une stratégie d'accès conditionnel, seuls des comptes de secours permettent de reprendre la main. Comme ils sont exclus de certaines protections, toute connexion avec eux doit déclencher une alerte.

Références : Microsoft Learn — Manage emergency access accounts in Microsoft Entra ID ; CIS M365 Foundations — 'Ensure two emergency access accounts have been defined'
MITRE ATT&CK : T1078.004 Valid Accounts: Cloud Accounts

Moyenne M365-CA-005 - Pas de stratégie basée sur le risque (connexion / utilisateur) alors que la licence P2 est présente (2 élément(s), Sous 30 jours)
Preuves
  • aucune stratégie active sur le risque de connexion (signInRiskLevels)
  • aucune stratégie active sur le risque utilisateur (userRiskLevels)

Pourquoi c'est important : Entra ID Protection calcule un niveau de risque (identifiants divulgués, IP anonyme, voyage atypique...). Sans stratégie qui exige la MFA ou bloque quand le risque est élevé, ces signaux restent de simples lignes dans un rapport que personne ne lit.

Remédiation : Créer deux stratégies d'accès conditionnel : risque de connexion élevé -> bloquer ou exiger la MFA ; risque utilisateur élevé -> bloquer ou exiger un changement de mot de passe sécurisé. Tester d'abord en mode rapport seul.

Licence : Nécessite Entra ID P2 : contrôle évalué uniquement si tenant.entraIdP2 = true (sinon ce n'est pas une mauvaise configuration mais une limite de licence).

Références : SCuBA MS.AAD.2.3v1 — Sign-ins detected as high risk SHALL be blocked ; SCuBA MS.AAD.2.1v1 — Users detected as high risk SHALL be blocked ; CIS M365 Foundations — Identity Protection sign-in risk / user risk policy recommendations (titres variables selon la version) ; Microsoft Learn — Risk-based access policies (Microsoft Entra ID Protection)
